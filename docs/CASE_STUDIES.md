# Case Studies

Здесь проекты описаны не как перечень технологий, а как инженерные кейсы: **контекст → проблема → ограничения → решение → доказательства → следующий шаг**.

> Принцип портфолио: планы, реализованный код и подтверждённый runtime не смешиваются между собой.

---

## 1. Service Automation & LeadRouter

### Контекст

Входящие обращения и сервисные заявки производственной компании приходят из нескольких каналов и должны корректно попадать в нужный бизнес-процесс. Ручная классификация и маршрутизация создают зависимость от конкретного сотрудника, а интеграции добавляют риск дублей, частично выполненных операций и ошибок при повторной доставке событий.

### Инженерная задача

Спроектировать контур, который:

- принимает и нормализует события из внешних систем;
- не запускает одну и ту же бизнес-операцию повторно;
- классифицирует обращения и выбирает маршрут;
- сохраняет результат и причину решения;
- различает временные технические ошибки и бизнес-ошибки;
- способен безопасно повторить операцию после timeout/5xx;
- не выдаёт наличие кода за доказательство production deployment.

### Ключевые решения

**DB-backed idempotency.** Входящее событие получает уникальную идентичность и фиксируется в базе до выполнения бизнес-обработчика. Повторное событие не должно запускать вторую классификацию или вторую бизнес-операцию.

**Транзакционные границы.** Бизнес-изменения и финальный статус обработки фиксируются атомарно. При ошибке бизнес-транзакция откатывается, а техническая ошибка сохраняется отдельно.

**Retry policy.** Временные сетевые ошибки не должны переводить бизнес-сущность в ошибочный бизнес-статус. Для retryable failure используется отдельный жизненный цикл повторных попыток.

**LLM как ограниченный компонент.** AI используется для классификации/маршрутизации, но результат проходит через структурированный контракт, confidence/status и safety-правила, а не напрямую управляет CRM без контроля.

**Evidence-first operations.** В документации разделены `PRODUCTION CONFIRMED`, `IMPLEMENTED`, `SCAFFOLD/INCOMPLETE` и `UNKNOWN`.

### Что можно подтвердить

- FastAPI backend;
- PostgreSQL + SQLAlchemy 2 async;
- Alembic migrations;
- Bitrix24 REST integration;
- DB-backed idempotency и transactional event processing;
- retry/failure model;
- LLM classification/routing в LeadRouter;
- GitHub Actions CI;
- **531 тест основного сервиса**;
- **590 тестов LeadRouter**;
- для части инфраструктуры отдельно зафиксирован runtime evidence.

### Что я не заявляю без дополнительных данных

- экономический эффект в рублях;
- процент сокращения ручного труда;
- абсолютную точность AI-классификации;
- полный production rollout всех компонентов.

Эти метрики будут добавляться только после фактического измерения.

### Что показывает кейс

Способность мыслить не отдельным endpoint'ом, а **полным жизненным циклом интеграционной операции**: повторная доставка → конкурентная обработка → транзакция → ошибка → retry → аудит → восстановление.

## 2. FlyPingAvia

### Контекст

Пользователь, ожидающий выгодную цену на авиабилет, вынужден многократно возвращаться к поиску и вручную проверять стоимость.

### Продуктовая задача

Сменить модель поведения пользователя с **«постоянно искать»** на **«один раз задать условие и получить сигнал»**.

### Решение

FlyPingAvia работает как price watcher:

1. пользователь задаёт маршрут, даты и ценовой порог;
2. подписка сохраняется;
3. scheduler запускает фоновые проверки;
4. price provider возвращает актуальные предложения;
5. при достижении порога пользователь получает уведомление;
6. переходы могут атрибутироваться для продуктовой аналитики и affiliate-модели.

### Ключевые решения

**Telegram Bot + Mini App.** Быстрый пользовательский вход без отдельной установки приложения.

**Signed Telegram initData.** Mini App не доверяет произвольному user ID от браузера; production-вход строится вокруг проверяемых Telegram-данных.

**Background checking.** Проверка цены отделена от пользовательского запроса и выполняется планировщиком.

**Production/development separation.** Временный tunnel допускается для разработки, но не должен случайно стать production URL.

**Health monitoring.** Системные проблемы и восстановление состояния выделены в отдельный эксплуатационный контур.

### Что можно подтвердить в публичном репозитории

- Python 3.11+;
- aiogram 3;
- FastAPI Mini App;
- SQLAlchemy;
- APScheduler;
- Travelpayouts integration / demo mode;
- Telegram signed initData auth;
- subscriptions и background price checking;
- deep-link attribution;
- health monitoring;
- Docker deployment examples;
- документация по Product Vision, Strategy, Architecture, Security, KPI, Monetization и Roadmap.

Публичный репозиторий: [FlyPingAvia](https://github.com/kirillq2098/FlyPingAvia)

### Что показывает кейс

Способность соединять **продуктовую гипотезу, backend, интеграции, фоновые процессы, безопасность, эксплуатацию и монетизацию** в одном продукте.

## 3. TopStyle Control

### Контекст

В производственно-строительной среде планирование часто распределено между таблицами, звонками, CRM/ERP и знаниями отдельных сотрудников. При изменении приоритетов сложно быстро увидеть влияние на производство, монтаж, зависимости и сроки.

### Задача

Создать отдельный управленческий слой для планирования и контроля проектов, не пытаясь без необходимости заменить существующие CRM/ERP-системы.

### Архитектурный подход

- web UI для единой точки просмотра;
- FastAPI как application/backend layer;
- PostgreSQL как системное хранилище;
- Alembic для контролируемой эволюции схемы;
- RBAC foundation для разграничения доступа;
- Docker Compose для воспроизводимого окружения;
- health/readiness для эксплуатационной проверки.

### Что подтверждено в репозитории

- Docker Compose environment;
- PostgreSQL;
- FastAPI backend;
- Next.js frontend;
- Alembic migrations;
- local authentication;
- RBAC foundation;
- health/readiness endpoints;
- PowerShell operational scripts;
- архитектурная и проектная документация.

Более поздние функции не считаются готовыми только потому, что присутствуют в roadmap или спецификации.

### Что показывает кейс

Способность начинать не с UI-макета, а с **границ системы, ролей, данных, интеграционной позиции и эксплуатационного фундамента**.

## Как я хочу развивать case studies

По мере появления реальных данных каждый кейс должен получать измеримые результаты:

- время процесса **до / после**;
- доля автоматической обработки;
- точность / precision / recall для AI-классификации;
- количество обработанных событий;
- SLA и error rate;
- стоимость LLM/API на операцию;
- бизнес-эффект;
- production SLO/availability, если метрика действительно измеряется.

Без измерения цифры в портфолио не добавляются.
