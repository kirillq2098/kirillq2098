# Проекты

Ниже — расширенные кейсы. Здесь намеренно разделены **подтверждённые факты**, **реализованный код** и **направление развития**. Это позволяет не выдавать планы за достижения.

## 1. Service Automation & LeadRouter

### Контекст

Внутренний проект автоматизации обработки входящих лидов и сервисных заявок производственной компании. Исходная среда включает Bitrix24, ручную маршрутизацию, разрозненные каналы входящих обращений и дальнейшие интеграционные сценарии с внутренними системами.

### Задача

Создать устойчивый контур, который способен:

- принимать события из внешних систем;
- нормализовывать входящие данные;
- предотвращать повторную обработку одного события;
- классифицировать и маршрутизировать лиды;
- сохранять трассируемость решения;
- корректно переживать сетевые и интеграционные сбои;
- отделять бизнес-ошибки от временных технических ошибок.

### Реализованные инженерные элементы

- FastAPI backend;
- async SQLAlchemy + PostgreSQL;
- Alembic migrations;
- DB-backed idempotency по входящим integration events;
- транзакционные границы для event processing;
- retryable / non-retryable error model;
- Bitrix24 REST integration;
- read-only discovery для CRM/SPA configuration;
- LeadRouter с LLM-классификацией и маршрутизацией;
- GitHub Actions CI;
- локальные production-safety правила и evidence review;
- явный client-agreement gate перед созданием/передачей инженерной задачи;
- stage-driven назначение ответственных в сервисном SPA;
- узкая retry-защита от race condition при bootstrap ServiceVisit/task binding;
- синхронизация заголовков SPA из авторитетного номера заказа 1С;
- ACT+DEFECT split flow с устойчивым reconciliation и контекстом исходной заявки;
- материалы/повторный выезд: readiness, возврат в планирование, reminder/retry flows и защита идентичности material cycle.

### Последние подтверждённые изменения

По merged PR и CI подтверждены:

- PR #24 — engineer handoff блокируется до явного согласия клиента;
- PR #25–27 — разделена identity маршрутного листа и номера 1С, добавлена синхронизация названий SPA/дочерних ACT-карточек из авторитетного номера заказа;
- PR #28 — ответственность по сервисным стадиям вычисляется из доменного состояния, а race при bootstrap выезда обрабатывается как retryable только в строго определённом окне;
- PR #29 — дочерняя карточка ACT+DEFECT получает краткий безопасный контекст исходной заявки; повторная обработка не создаёт дублирующий комментарий.

### Подтверждённые метрики репозитория

Последний проверенный GitHub Actions run:

- основной сервис: **915 passed, 4 skipped**;
- LeadRouter: **590 passed**;
- оба CI job завершились со статусом **success**.

Важно: это доказательство состояния кода и CI. Оно не означает, что последние изменения уже развернуты в production.

### Почему этот проект важен

Он не сводится к одному API endpoint. Основная ценность — проектирование **надёжного процесса между бизнес-системами**, где повторный webhook, timeout, lost ACK, race condition или частично выполненная операция не должны приводить к дублированию или повреждению бизнес-состояния.

### Стек

`Python` · `FastAPI` · `PostgreSQL` · `SQLAlchemy 2 async` · `Alembic` · `Bitrix24 REST` · `LLM` · `Docker` · `GitHub Actions`

## 2. FlyPingAvia

### Продукт

Сервис, который снимает с пользователя необходимость постоянно вручную проверять стоимость авиабилетов.

Пользователь задаёт маршрут и цену, за которую готов купить билет. Система периодически проверяет предложения и уведомляет, когда цена достигает заданного порога.

### Реализовано

- Telegram-бот;
- Telegram Mini App;
- signed `initData` authentication;
- управление подписками на маршруты;
- гибкие даты;
- фоновая проверка цен;
- интеграция с Travelpayouts;
- affiliate/deep-link attribution;
- health monitoring и recovery alerts;
- production/development configuration separation;
- Docker deployment examples;
- документация по стратегии, монетизации, UX, безопасности, KPI и roadmap.

### Продуктовый подход

FlyPing проектируется не как ещё один каталог авиабилетов, а как **price watcher**: пользователь один раз задаёт условие, после чего система ждёт нужную цену вместо него.

### Стек

`Python 3.11+` · `aiogram 3` · `FastAPI` · `SQLAlchemy 2` · `APScheduler` · `httpx` · `Telegram Mini App` · `Travelpayouts` · `Docker`

### Репозиторий

https://github.com/kirillq2098/FlyPingAvia

## 3. TopStyle Control

### Контекст

Проект внутренней системы управления строительными и производственными проектами. Цель — заменить фрагментированное ручное планирование единым контуром, где можно видеть структуру объекта, работы, сроки, зависимости, прогресс, блокеры и риски.

### Архитектурная идея

Система не должна без необходимости заменять Bitrix24, 1С или другие действующие инструменты. Она проектируется как **управленческий слой**, агрегирующий планирование и контроль исполнения.

### Подтверждённая базовая реализация

- Docker Compose environment;
- PostgreSQL;
- FastAPI backend;
- Next.js frontend;
- Alembic migrations;
- local authentication;
- RBAC foundation;
- health/readiness endpoints;
- операционные PowerShell scripts;
- архитектурная и проектная документация.

Некоторые более поздние идеи и модули находятся в развитии и не перечисляются здесь как завершённые без фактического подтверждения в репозитории.

### Стек

`FastAPI` · `Next.js` · `PostgreSQL` · `Alembic` · `Docker Compose` · `RBAC`

## Как читать эти кейсы

Это портфолио намеренно не использует формулировки вроде «создал production AI-платформу», если этому нет достаточного runtime evidence. Для каждого проекта важно различать:

1. **идею и бизнес-задачу**;
2. **спроектированную архитектуру**;
3. **реализованный и протестированный код**;
4. **подтверждённый production runtime**;
5. **измеримый бизнес-результат**.

По мере появления фактических метрик — экономия времени, SLA, качество классификации, conversion impact, число активных пользователей — они будут добавляться отдельно.
