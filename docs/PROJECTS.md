# Проекты

Здесь собраны проекты, которые лучше всего показывают мой подход: **сначала реальная проблема, затем решение, проверка и только после этого — технологии**.

Я намеренно разделяю три вещи: что уже реализовано, что подтверждено тестами/CI/runtime и что пока остаётся следующим этапом. Это помогает не превращать портфолио в список обещаний.

---

## 1. Service Automation & LeadRouter

### Проблема

Сервисные заявки и входящие лиды проходят через CRM, сотрудников и внешние системы. В таком процессе опасны не только ошибки пользователя, но и повторные webhook, сетевые сбои, дублирование операций и частично выполненные действия.

### Решение

Я спроектировал контур, где входящие события нормализуются, повторная обработка контролируется через БД, технические ошибки отделены от бизнес-ошибок, а AI используется для классификации и маршрутизации, но не получает бесконтрольного доступа к бизнес-процессу.

Отдельная часть проекта автоматизирует сервисный процесс: согласование выезда, назначение ответственных, работу с материалами, повторные визиты и связь между карточками Bitrix24.

### Почему это важно

Система должна корректно работать не только в «идеальном» сценарии, но и когда webhook пришёл дважды, внешний API ответил с задержкой или операция оборвалась посередине.

### Evidence

- основной сервис: **915 тестов passed, 4 skipped** в последнем проверенном CI;
- LeadRouter: **590 тестов passed**;
- GitHub Actions CI подтверждён;
- для LeadRouter отдельно подтверждались Cloudflare ingress и публичный health endpoint;
- новые функции не считаются production-развёрнутыми без отдельного runtime evidence.

**Стек:** Python, FastAPI, PostgreSQL, SQLAlchemy, Alembic, Bitrix24 REST, LLM, Docker, GitHub Actions.

## 2. TopStyle Planning

### Проблема

Когда производство, монтаж, сроки объектов и приоритеты заказчиков планируются в нескольких таблицах и через ручные договорённости, любое срочное изменение быстро ломает общий план.

### Решение

Отдельная корпоративная система планирования связывает объект с этапами работ, контрольными точками, зависимостями, готовностью, проектированием, материалами, производством, доставкой и монтажом.

Следующий уровень — недельное распределение производственной мощности. Система рассчитывает потребность от монтажного графика, учитывает приоритет клиентов и распределяет доступный объём до объекта, секции и этажа. При этом предложение не становится утверждённым планом автоматически — его подтверждает человек.

### Почему это важно

Руководитель видит не просто список заказов, а **что нужно произвести, к какой неделе, для какого объекта и что произойдёт при нехватке мощности**.

### Evidence

- модульный монолит на **.NET 10 / ASP.NET Core 10**;
- PostgreSQL и миграции;
- Phase 15–26 отмечены в репозитории как COMPLETE / ACCEPTED;
- реализованы milestones, dependencies, baselines, readiness, design, materials, production, delivery, installation, tenders и change scenarios;
- repeatable импорт Plan 26 загрузил **25 объектов** и связанные плановые данные;
- принятие Phase 26 завершилось с **525 passed tests**;
- APS solver отдельно помечен как deferred, развитие после Phase 26 приостановлено.

**Стек:** .NET 10, ASP.NET Core 10, PostgreSQL, Blazor/веб-интерфейс, GitHub Actions.

## 3. TopStyle Control

### Проблема

Для управления строительными и производственными объектами недостаточно видеть только задачи или CRM-карточки. Нужен общий слой, где одновременно видны структура проекта, сроки, зависимости, прогресс, блокеры и риски.

### Решение

TopStyle Control создавался как управленческий контур поверх существующих систем, а не как попытка заменить CRM и ERP.

### Почему это важно

Такой подход позволяет постепенно цифровизировать управление, не требуя сначала переписать всю инфраструктуру компании.

### Evidence

Подтверждены базовые компоненты: FastAPI backend, Next.js frontend, PostgreSQL, Alembic, Docker Compose, local authentication, RBAC foundation, health/readiness и операционные скрипты.

**Стек:** FastAPI, Next.js, PostgreSQL, Alembic, Docker Compose, RBAC.

## 4. LeadHunter

### Проблема

Поиск заказов на автоматизацию, AI, сайты и интеграции вручную занимает много времени, а большая часть найденных публикаций либо не является реальным запросом клиента, либо не подходит по услуге и контакту.

### Решение

LeadHunter автоматически собирает потенциальные заявки из публичных источников, удаляет дубли, классифицирует их и показывает только те, которые проходят заданные фильтры.

Источники включают FL.ru RSS и явно заданные публичные Telegram-каналы; дополнительно может использоваться Brave Search. После отбора сильная заявка попадает в Telegram. Ответ клиенту не отправляется автоматически: после подтверждения создаётся Gmail-черновик.

### Почему это важно

Цель проекта — не «найти как можно больше лидов», а **сократить шум и оставить только те заявки, на которых потенциально можно заработать**.

### Evidence

- детерминированный сбор из FL.ru RSS и публичных Telegram-источников;
- deduplication по нормализованному URL;
- rule-based и OpenAI classification modes;
- scoring и Telegram notification flow;
- FastAPI API и SQLite для MVP;
- human approval перед созданием Gmail draft;
- автоматическая отправка клиентам намеренно отсутствует.

**Стек:** Python, FastAPI, SQLite, Telegram Bot API, Gmail API, OpenAI, RSS.

## 5. 100K30

### Проблема

Технический проект сам по себе не доказывает, что решение можно продать. Нужен отдельный эксперимент, где гипотеза проверяется реальным рынком: найти проблему компании, подтвердить её, выйти на контакт и получить деньги.

### Решение

100K30 — 30-дневный evidence-first эксперимент с целью получить **100 000 ₽ выручки** на услугах автоматизации и AI.

Вместо массовой рассылки проект ищет конкретные visibility/recommendation gaps, фиксирует доказательства, проводит human verification и только после этого разрешает outreach.

### Почему это важно

Это проверка не только инженерных навыков, но и полного цикла **исследование → гипотеза → доказательство → предложение → контакт → обратная связь → выручка**.

### Текущее evidence-состояние

На **2 октября 2026** в репозитории зафиксировано:

- **50 prospects**;
- **34 human-verified / qualified**;
- **32 unique contacted prospects**;
- **34 подтверждённых Gmail send events**;
- **1 живой ответ**;
- meetings: 0;
- proposals: 0;
- paid clients: 0;
- revenue: **0 ₽**.

Проект находится в активной проверке гипотезы. Нулевая выручка не скрывается и не трактуется как успех — это текущий измеримый результат эксперимента.

**Подход:** Revenue First, evidence-first, Human Verification Gate, LLM LAST.

## 6. FlyPingAvia

### Проблема

Человек, который ждёт выгодную цену на авиабилет, вынужден снова и снова открывать поиск и проверять стоимость.

### Решение

FlyPingAvia меняет сценарий: пользователь один раз задаёт маршрут и цену, за которую готов купить билет, а система сама проверяет предложения и уведомляет при достижении порога.

### Почему это важно

Продукт убирает повторяющееся действие пользователя и превращает поиск билетов в понятную модель **«задал условие → дождался сигнала»**.

### Evidence

В публичном репозитории есть Telegram Bot и Mini App, signed Telegram initData authentication, subscriptions, background price checking, Travelpayouts integration/demo mode, affiliate/deep-link attribution, health monitoring и Docker deployment examples.

[Открыть публичный репозиторий →](https://github.com/kirillq2098/FlyPingAvia)

**Стек:** Python, aiogram, FastAPI, SQLAlchemy, APScheduler, Telegram Mini App, Travelpayouts, Docker.

## Как я оцениваю зрелость проекта

Для каждого проекта я различаю:

1. **идею и бизнес-задачу**;
2. **реализованный код**;
3. **тесты и CI**;
4. **подтверждённый runtime / production**;
5. **измеримый бизнес-результат**.

Наличие кода не означает production, а количество тестов не заменяет бизнес-метрики. Поэтому портфолио обновляется только тогда, когда появляется новое подтверждаемое evidence.
